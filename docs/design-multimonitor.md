# マルチモニタ対応の仕様・設計

状態: 案（第 2 版。Fable 5.2 のレビューを反映）。`docs/design-p3.md` §8「別ウィンドウ（FR-L7）」を具体化する。

## 1. 目的と方針

- 2 枚目のモニタに「見続けたいもの」を置き、1 枚目では探す・選ぶ作業を続けられるようにする。
- キーボードだけで、ウィンドウを開く・移る・閉じることができる（FR-KB4）。
- 1 枚のモニタの利用者には何も増やさない（今の操作・見た目・保存の形はそのまま）。
- データは終値ベース（日中は気配の仮の足）なので、2 枚目は「刻々の監視」ではなく **1 枚目の操作についてくる表示** を主にする。

## 2. 今の構造で 1 ウィンドウ前提になっているところ

## 3. アーキテクチャ

### 3.1 ウィンドウ: どの窓も同じ renderer、主と子のスロット

- 子ウィンドウも今と同じ renderer のバンドル（別の小さなアプリは作らない。ペイン・キー・ヘルプ・テストを 1 つに保つ）。
- ウィンドウは **固定のスロット**: 主（`main`）と子（`w1`、のちに `w2`…）。最初の版は **子 1 枚**。
- renderer は自分のスロットを URL で知る（`index.html?w=w1`）。落ちて読み込み直しても同じスロットに戻る。
- 主ウィンドウだけが行うこと: 初回起動の確認、更新の確認、自動更新のタイマー、ジョブの完了などの知らせの既定の出し先。
- 子ウィンドウを閉じても、そのスロットの配置とレイアウトは残る（次に開けば元どおり）。アプリの終了で閉じた子ウィンドウは、次の起動で開き直す。利用者が閉じた子ウィンドウは開き直さない。
- 主ウィンドウを閉じるとアプリを終える（確認は出さない。次の起動で全部戻る）。子ウィンドウには `parent` を付けない（主の上に固定されないように）。

### 3.2 Core: ウィンドウごとのポート

- `ports: Map<slot, Port>`。要求には **来たポートへ** 返事、イベント（ジョブの進み・データの更新・利用者のデータの変更）は **全ポートへ**。
- 同じスロットから新しいポートが来たら（読み込み直し）、古いポートを閉じて置き換え、そのスロットの「表示中の銘柄」（`jobs.prioritize`、FR-F8）を捨てる。表示中の銘柄はスロットごとに受けて和集合で使う。
- Core が落ちて立ち上げ直したら、main が全スロットに配線し直し、各ウィンドウは `core.ready` で全部を読み直す。

### 3.3 状態の同期

| 種類                      | 例                                                         | 正（持ち主）    | 書き方                                                                     | 配り方                                                                                                                                                                                                                                                                     |
| ------------------------- | ---------------------------------------------------------- | --------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 利用者のデータ            | 設定・ウォッチリスト・スクリーン・保有・名前付きレイアウト | **Core**        | 今の保存 API（はじめは後勝ち）。返事に `rev` を付ける                      | Core がイベント `user.changed { kind, data, rev }` を全ウィンドウへ。受けた窓は **その kind の保存待ち（デバウンス）を先に送ってから**、`rev` が自分の持つものより新しいときだけ置き換える。開いている下書き（設定のダイアログ・スクリーナーの編集中の条件）は上書きしない |
| ウィンドウのレイアウト    | タブ・ドロワー・区切り                                     | 各ウィンドウ    | **`user.saveWindowLayout { slot, … }`**（自分の分だけ）                    | 配らない                                                                                                                                                                                                                                                                   |
| リンク（リンク色 → 銘柄） | 1 枚目で選んだ銘柄を 2 枚目が追う                          | **main のバス** | `bus.publish('link', …)`。保存は送った窓が Core の **`user.saveLinks`** で | main が番号を付けて他の窓へ。最後の値を覚え、あとから開いた窓・読み込み直した窓に渡す                                                                                                                                                                                      |
| フォロー（一覧の並び）    | スクリーナーの結果をチャートウォールで                     | main のバス     | `bus.publish('follow:<link>', ids)`（間引き・上限あり）                    | 同上。保存しない                                                                                                                                                                                                                                                           |

- **バスは main に置く**（30 行ほど）。BroadcastChannel は同じオリジンなら届くが、順番の保証・あとから来た窓への再送が無い。Core を通すと、同期的な SQLite の処理（スクリーニング・指標）の間リンクの追従が止まる。
- **こだまを防ぐ**: 受けたリンクは `applyRemoteLink` で反映し、保存もバスへの送り直しもしない。リモートのリンクで一覧が行を選び直しても送り直さない。
- ウォッチリストの「足す・外す・並べ替え」を操作単位の API にするのは第 2 段階（R2）。それまでは後勝ちで、ずれは保存のたびの配信で数十 ms に収まる。
- 設定（テーマ・文字の大きさ・キーの割り当て）は全ウィンドウに即時に効く。ウィンドウごとに `uiScale` だけは別に持てる（遠い 4K の画面のため）。
- ダイアログ・トースト・フォーカス・最大化はウィンドウごと。知らせは main が「いま前にあるウィンドウ」を各窓に伝え、それが無ければ主ウィンドウに出す。

### 3.4 レイアウトの保存: 今の形に足すだけ（版を壊さない）

```ts
interface LayoutDoc {
  version: 1 | 2
  active: PresetId // 主ウィンドウ（今と同じ）
  entries: Record<PresetId, LayoutEntry> // 主ウィンドウ（今と同じ）
  links: Record<string, InstrumentId> // 全ウィンドウ共有（今と同じ）
  windows?: Record<
    'w1' | 'w2' | 'w3',
    {
      // 足すだけ
      entry: LayoutEntry // 子ウィンドウは 1 つのレイアウト（タブを持たない）
      preset?: SecondaryPreset // 開いたときの元（詳細・ウォール・タブの写し）
      uiScale?: number
    }
  >
}
```

- 主ウィンドウの形は変えない。古い版のアプリで開いても主のレイアウトは消えない（`windows` を知らないだけ）。
- ペインの ID は全ウィンドウで重ならない（`normalizeDoc` の重複の検査を `windows` にも広げる）。
- 「最近閉じたウィンドウ」は作らず、スロットにレイアウトが残ることで代える。

## 4. 2 枚目で提供するもの

### 4.1 子ウィンドウの開き方（Ctrl+Alt+N で選ぶ）

| 名前                             | 中身                                                           | 1 枚目との関係                                              | 想定                                                                                    |
| -------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **詳細**                         | 日・週・月のチャート + 銘柄情報（大きく、10 年分の配当の推移） | リンク 1 についてくる（1 枚目の一覧・グリッドで選んだ銘柄） | 1 枚目で一覧をめくり、2 枚目で 1 銘柄をじっくり。いちばん効果が大きく、作るものが少ない |
| **チャートウォール**             | チャートグリッド（全画面向け）                                 | リンク 1 の一覧を **フォロー**（§4.2）                      | スクリーニングの結果・ウォッチリストをまとめて眺める                                    |
| **今のタブを新しいウィンドウで** | 今のタブ（マーケット・保有・インカムなど）の写し               | タブのリンクのまま                                          | 監視用の専用の画面は作らず、既存のタブをそのまま 2 枚目へ                               |

- 「マーケット監視」「保有モニタ」のような専用の画面は作らない（終値ベースなので刻々の監視の意味が薄い。既存のタブの写しで足りる）。

### 4.2 フォロー（チャートウォール）

- 元: **リンク 1 で、最後にフォーカスした一覧のペイン**（スクリーナーの結果・ウォッチリスト・ランキング・保有）。チャートにフォーカスを移しても元は変わらない（ウォールが空にならない）。
- 一覧は「いまの並び」（並べ替えた順の銘柄 ID）をバスに送る（間引き 200ms・上限 300 件）。
- ウォールの見出しに元の名前と件数（例: 「スクリーナー: 高配当銘柄 · 32 件」）。**固定**（P、今の「今の銘柄で固定」と同じ）でフォローを止めて写し取る。
- 1 枚目で選んだ行のタイルを強調し、見えていなければそのページへめくる。
- 逆向き: ウォールのタイルを選ぶとリンク 1 が変わり、1 枚目の一覧はその行を選ぶ（フォーカスは奪わない）。

| 操作                                                                                   | キー                                                                   |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 新しいウィンドウ（詳細・ウォール・今のタブを選ぶ）                                     | **Ctrl+Alt+N**                                                         |
| 次・前のウィンドウへ（そのウィンドウで最後にフォーカスしたペインへ、キー操作の枠つき） | **Ctrl+F6 / Ctrl+Shift+F6**（F6 はウィンドウの中のペインを巡る、と対） |

| 全画面                                                                                 | F11（ウィンドウごと）                                                  |

## 5. 位置の記憶と戻し

- `window.json` を版 2 に: **ディスプレイの組み合わせ（全ディスプレイの位置・大きさ・倍率を並べたもの）ごと** に、各スロットの位置・最大化・全画面を持つ。ディスプレイの `id` や名前には頼らない（ドッキング・ドライバで変わる・同じ名前が多い）。
- 置き方は純粋な関数 `place(displays, saved) → bounds` にして単体で試す。記録が無い組み合わせ（ノートを持ち出したなど）では子ウィンドウを主ディスプレイの見える位置に寄せ、**元の組み合わせの記録は上書きしない**（戻ってきたら元の位置に戻る）。
- 動作中に `display-removed` が来たら、その画面にあった窓は全画面を解いて主ディスプレイへ。この移動の位置は記録しない。
- 倍率の違う画面へは「先に置く → 大きさを合わせる → 確かめる」の順。キャンバスのタイルは `devicePixelRatio` が変わったら描き直す。

## 6. 段階

| 段階               | 中身                                                                                                                                                                                                                                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **R1**（最初の版） | Core のウィンドウごとのポート。`user.changed`（後勝ち・保存待ちを先に送る・下書きを守る・`core.ready` で読み直し）。ウィンドウごとのレイアウト保存とリンクだけの保存。WindowManager（子 1 枚）・主だけの処理・IPC の送り元化。main のバス（リンク）。**詳細**と**今のタブを新しいウィンドウで**。Ctrl+Alt+N・Ctrl+F6。位置の記憶と戻し |
| R2                 | **チャートウォール**とフォロー（強調・自動のページ送り・逆向き）。ウィンドウごとの `uiScale`。ウォッチリストの操作単位の保存                                                                                                                                                                                                           |
| R3                 | 子ウィンドウを増やす（w2・w3）。ペインを別ウィンドウへ出す・戻す。ウィンドウをまたぐ十字線の同期・ドラッグ                                                                                                                                                                                                                             |

## 7. テスト

- 単体: `normalizeDoc`（`windows` の正規化・ペイン ID の重複・版 1 のまま開ける）、`place()`（組み合わせの一致・持ち出し・戻り・画面外）、`user.changed` の適用（古い `rev` を捨てる・保存待ちを先に送る）、バスの番号と最後の値。
- E2E（Playwright `_electron`）: `app.waitForEvent('window')` で子ウィンドウを取り、キーだけで開く・リンクの追従・閉じて開き直す・再起動で戻る。**Ctrl+F6 の確かめは OS の前面ではなく main の「いま前にある窓」の状態で**（`electronApp.evaluate`）。CI の前面の扱いが不安定なため。
- 固定データ: 版 1 の `window.json`、画面外の位置、版 2 で保存したあと古い版で開く（主のレイアウトが消えないこと）。

## 8. リスク・未決

- 状態の同期の作り替え（R1）が一番大きい。保存関数を `stores/app.svelte.ts` に集めてから入れる。
- メモリ: 窓ごとに銘柄の一覧・指標のキャッシュを重ねて持ち、`data.updated` で窓の数だけ読み直す。R1 で実測して `docs/decisions.md` に書く（150〜250MB/窓は見込み）。
- 終了: main は全ウィンドウの `beforeunload` の完了を知れないので、今の 150ms の猶予を保つか、明示のフラッシュと応答を足す。
- 描画: グリッドのタイルは Canvas 2D で描くので、6×5 のウォールでも WebGL の数の上限は問題にならない見込み（R2 で実測）。
