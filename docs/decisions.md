## SQLite のインデックスは足さない（2026-11-28）

日足・月足・`actions` は主キー `(id, 日付…)` の WITHOUT ROWID、スクリーナーは `metrics` を全件読んでメモリで判定する。銘柄ごとの読み書きは主キーで足りる。
主キーが向かないのは日付だけで絞る `DELETE FROM daily_bars WHERE d < ?` と同じ条件の `COUNT` で、使うのは保存期間を短くしたとき（`jobs.applyRetention`・`jobs.planRetention`。FR-D6）だけ。
月足を日付で消す処理は無い（銘柄ごとだけ）。統計は終了のたびの `PRAGMA optimize` が作るので、`ANALYZE` も足さない。

実測（手元の DB を `VACUUM INTO` で写したもの。日足 388 万行・1,633 銘柄・2016-10 から。消したあとは ROLLBACK）:

| 処理                                             | 時間                            |
| ------------------------------------------------ | ------------------------------- |
| `COUNT(*) … WHERE d < ?`（306〜346 万行）        | 0.16〜0.18 秒                   |
| `DELETE … WHERE d < ?`（今のまま）               | 0.55〜0.89 秒                   |
| 銘柄ごとに `DELETE … WHERE id = ? AND d < ?`     | 0.56 秒（変わらない）           |
| `CREATE INDEX daily_bars_d ON daily_bars(d)`     | 1.5 秒                          |
| そのインデックスがあるときの `DELETE … d < ?`    | 22 秒（インデックスも消すため） |
| 削除のあとの `wal_checkpoint`・`VACUUM`          | 1.4 秒                          |

- 実行計画は表の全件の走査ではなく `SEARCH daily_bars USING PRIMARY KEY (ANY(id) AND d<?)`（`sqlite_stat1` による skip-scan）。
- 削除のあとに VACUUM と指標の作り直し（`recomputeAll`）が続くので、削除だけを速くしても待ちはほとんど変わらない。
- `metrics` の列へのインデックス（全件をメモリで判定するので使われない）・`daily_bars(id, d)`（主キーと同じ）・`cache_size`・`mmap_size` の変更も入れない。
- 日付だけで消すのが遅くなったら（行が大きく増えたとき）、インデックスではなく、統計が無いときの実行計画と銘柄ごとの削除から見直す。

## Yahoo への間隔を 0.4 秒に縮める（2026-11-23）

数日起動しなかったあとの日々の更新が、全銘柄の日足を 1 銘柄ずつ取り直して約 40 分かかっていた（[design-daily-update.md](design-daily-update.md)）。
取りこぼしの埋め方を変える案（spark の終値・補う範囲を絞る）は採らず、間隔だけを縮める（スクリーニングで全銘柄を使うので、範囲は絞らない）。

| 項目           | 判断                                                                                                                                                                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 間隔           | 0.4 秒 + 0〜0.15 秒の揺らぎ（前は 1.0 秒 + 0〜0.3 秒）。`src/shared/pace.ts` の定数。**うまくいかなくなったら `YAHOO_INTERVAL_MS = 1000`・`YAHOO_JITTER_MS = 0` にするだけで前の速さに戻る**（揺らぎは無くなる。前と同じにするなら 300。ほかのコード・テストは変えなくてよい）                                                           |
| 並列           | しない。`throttle()` は送り始めた時刻から間隔を空け、応答（中央値 130ms）は間隔の中に隠れるので、2 本並べても Yahoo から見た速さは間隔を縮めたのと同じ。直列ならジョブのループを変えずに済む                                                                                                                                             |
| 429 のとき     | 24 時間は 1.0 秒 + 0〜0.3 秒に落とし、今のバックオフも続ける。そのあと（再起動のあとも）0.4 秒から試し直す（常駐で Core が何週間も動き続けても戻るように）。遅い間隔が最小間隔以下なら落とさない（定数を 1 秒に戻したとき）。429 は HTTP の状態・「status 429」・TooManyRequests・rate limit で見分け、本文の中の数字の 429 では当てない |
| 所要時間の案内 | 初回の取得・全データの取り直しの「約 N 分」は同じ定数から作る（`fetchMinutes`・`firstRunEstimate`。1 回あたり 間隔 + 揺らぎの平均 + 50ms）                                                                                                                                                                                               |
| 見込み         | 4 日空けたときの日々の更新 約 40 分 → 約 15 分、初回の取得（日足）約 35〜40 分 → 約 15 分。NFR-P6（5 分以内）は数日空けたときには満たさない                                                                                                                                                                                              |

実測（2026-11-23 01 時、日曜。手元の DB の取得の対象 4,444 銘柄から均等に選んだ 300 銘柄、`v8/finance/chart` の日足 20 日分、直列。値は保存していない）:

| 項目         | 結果                                                     |
| ------------ | -------------------------------------------------------- |
| 応答         | 200 が 297 件・404 が 3 件（データの無い銘柄）。429 は 0 |
| かかった時間 | 144.9 秒（1 回あたり 0.483 秒）                          |
| 応答の時間   | 中央値 130ms・90% 点 144ms・最大 313ms                   |

平日の大引け後・1,650 回続けたときは測っていない（利用者の判断で、この結果で入れる）。調べたこと（yahoo-finance2 の `queue`・yfinance の 429 の報告）は
design-daily-update.md §6。

## TOPIX の代わりの ETF を 1306 から 1308 に替える（2026-11-22）

TOPIX は Yahoo で取れないので連動 ETF で代えている（FR-U6）。1306 の日足は、2026-03-30 の 10:1 の分割の前後で Yahoo の調整が
二重にかかっている（3/30・3/31 の終値が 37 円台で、前後は 380 円台。出来高も 10 倍）。米国の Yahoo Finance の履歴のページも同じ値で、
日本の Yahoo!ファイナンス（別のデータ）だけが正しい。週足は正しい。1475 も 2024-08-08 の分割で同じ形の誤りがある。
yfinance は `repair=True`（`_fix_bad_stock_splits`）で補正するが、yahoo-finance2 には補正が無い。場当たり的な補正は入れず、分割の無い ETF に替える。

主な TOPIX 連動 ETF の Yahoo のデータ（日足は 2023-10 以降、月足は上場以来。跳ねは前日比・前月比 ±30% 超）:

| ETF                                    | 売買代金（直近 60 日の平均） | 分割         | データの跳ね                                   |
| -------------------------------------- | ---------------------------- | ------------ | ---------------------------------------------- |
| 1306 NEXT FUNDS                        | 72.6 億円                    | 2026-03 10:1 | 日足 2026-03-30・31、月足 2014-12・2026-02・03 |
| 1475 iShares Core                      | 15.8 億円                    | 2024-08 10:1 | 日足 2024-08（同じ二重の調整）                 |
| **1308 上場インデックスファンドTOPIX** | **9.5 億円**                 | なし         | なし（月足 2007-12〜）                         |
| 1305 iFreeETF TOPIX                    | 5.1 億円                     | なし         | なし（月足 2007-12〜）                         |
| 1348 MAXIS TOPIX                       | 4.3 億円                     | なし         | なし（分配が年 2 回）                          |

- 1308 にする（分割が無く、日足・月足とも跳ねが無い。分配は年 1 回。売買代金は 1306 の次に多い）。定数は `src/shared/markets.ts` の `TOPIX_ETF` の 1 か所。
- 保存した値で TOPIX の代わりを ID で持つのは、パフォーマンス比較の比べる相手（`pfBench`）だけ。比べる相手でない ID は `TOPIX_ETF` として読む
  （1306 かどうかは見ない）。ポートフォリオの比べる相手は番号で持つので、そのまま 1308 を指す。マーケットのペインで利用者が並べた 1306 は、
  利用者が選んだ銘柄として残す。

## P2 の実装判断（2026-11-13、v0.0.2）

| 項目                          | 判断                                                                                                                                                                                                                                                                        | 理由                                                                                                                                                                         |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQLite の読み書きの見直し     | 指標の再計算は直近 800 本の日足と最初の日付だけを読み、100 銘柄ごとに処理を譲る。グリッドのタイルは要る本数だけ読む。準備した文を使い回す（200 件まで）。VACUUM のあとも WAL を空にし、`journal_size_limit` を 64MB にする。キーの整数化（DB −28%）は影響が大きいので見送り | 1,700 銘柄 × 10 年（420 万行）で測った: 全銘柄の再計算の読み出し 4.9 秒 → 0.9 秒、30 タイル 47ms → 15ms。VACUUM 後に DB と同じ大きさの WAL が残り、使用量が 2 倍に見えていた |
| 保有の手数料・税（FR-H5）     | 手数料は買いの取得価額に含め、売りの手数料と税は含めない                                                                                                                                                                                                                    | 証券会社の「平均取得単価」の表示に近く、税は口座区分（NISA・特定）で変わるため                                                                                               |
| 直接入れた保有に取引を足す    | 今の数量・単価を、入れた日付の買いの取引として残してから足す                                                                                                                                                                                                                | 入れた値は今の基準なので、それより前の分割で調整されないように                                                                                                               |
| 保有の保存先                  | 利用者のデータ（`holdings.json`）。市場データの DB とは分け、全体の書き出し（`user.exportAll`）にも入れない                                                                                                                                                                 | 個人の資産情報なので、専用の書き出し（注意の表示つき）だけにする（FR-H10）                                                                                                   |
| 「または」の意味（FR-SC5）    | 「または」はすぐ上の条件とまとめ、まとまりどうしを「かつ」でつなぐ（積和形）                                                                                                                                                                                                | キーだけで組め（A で切り替え）、条件の並びで読めるため。括弧の入れ子は持たない                                                                                               |
| 相対条件（FR-SC5）            | 同じ単位（金額・%）の市場データの指標どうしだけ。値は相手からの差（%）                                                                                                                                                                                                      | 単位の違う比較（利回り ≥ PBR など）は意味が無いため                                                                                                                          |
| 指標の追加（P2）              | 移動平均（25/75/200）・52 週高値安値・配当性向・連続増配 / 非減配の年数・クロスからの日数・2 期の年換算利回り・異常値を metrics 表に足し、DB を v2 に上げて表を作り直す                                                                                                     | metrics は日足から作り直せる派生の表なので、移行より作り直しが確実                                                                                                           |
| 連続増配の数え方              | 暦年（権利落ち日）ごとの合計で比べ、保存期間の範囲内で数える                                                                                                                                                                                                                | 決算期の違う銘柄でも同じ物差しで比べられ、保存期間を超える年数は主張しない                                                                                                   |
| キーの割り当て（FR-KB6）      | 変えられるのはアクションの登録表のキーだけ。Ctrl か Alt 付き、または F1〜F12 に限る                                                                                                                                                                                         | 単キーはペインの中の操作（一覧の S、チャートの D/W/M など）に使っているため                                                                                                  |
| 名前付きのレイアウト          | マイレイアウトのタブのページにする（2026-11 に統合。どのタブにも読み込む形はやめた。docs/design-mylayouts.md）                                                                                                                                                              | プリセット（Ctrl+Shift+1〜8）の切り替えとの関係を単純に保つ                                                                                                                  |
| ドラッグでのタブ化（FR-L2）   | 本体の中のタブ化はせず、ドロワーに落とすとタブになる                                                                                                                                                                                                                        | 本体はタイル型の分割に揃え、タブはドロワーに集める                                                                                                                           |
| 一目均衡表の雲                | 先行スパン 1・2 を線で描き、塗りはしない                                                                                                                                                                                                                                    | Lightweight Charts の系列だけで描け、30 枚のグリッドの性能に影響しない                                                                                                       |
| 比較表示（FR-C7）             | 右の目盛りを「表示の始点を 0% とした %」に切り替え、最大 5 銘柄を重ねる                                                                                                                                                                                                     | Lightweight Charts の Percentage モードで、表示期間を変えても始点が追従する                                                                                                  |
| 自動更新（FR-F6）             | 大引けの 30 分後（16:00）から、最後の更新が直近の大引けより前なら、起動時と 5 分ごとに確かめて更新する                                                                                                                                                                      | 一括気配が大引けの値に落ち着くまでの余裕を見る                                                                                                                               |
| 新しい版の通知（NFR-Q9）      | Core が api.github.com の最新リリースだけを見る（設定で切れる）。スタブのデータ源では通信しない                                                                                                                                                                             | 許可リストの通信先を 1 つ増やすだけで済み、利用者の情報は送らない                                                                                                            |
| 見た目の回帰テスト（NFR-Q10） | 主要なダイアログ（初回・F1・設定）をダークとライトで要素ごとに撮る                                                                                                                                                                                                          | チャートや時計は日付で変わり、毎日の CI で揺れるため                                                                                                                         |
| ログ（NFR-O1）                | main も userData/data/logs に日付ごとのファイルを書き、30 日より古いものは消す                                                                                                                                                                                              | Core のログと同じ場所にまとめ、設定とコマンドバーから開ける                                                                                                                  |
| フォーカスの枠（FR-KB3）      | ペイン・タイルの枠は `:focus-visible` と同じく、キーで操作しているときだけ出す（最後の入力がキーかポインタかを `<html data-input>` に持つ）。クリックし直して外す方式は、キー操作の行き先が見えなくなるので採らない。設定で常に出せる                                       | VS Code・Figma・Linear など最近のアプリの作法。マウス利用者には枠が邪魔で、キーの利用者には要る                                                                              |

## P0 下調べ（2026-11-13）

環境: Windows 11、Node 25.9.0、Electron 45.3.1（Node 24.22.2 / Chromium 156）、yahoo-finance2 4.0.6、lightweight-charts 5.3.0。調査用のスクリプトはリポジトリに入れていない（使い捨て）。

### 1. Yahoo Finance（yahoo-finance2）で取れるもの

調べた銘柄: 7203 トヨタ、8058 三菱商事、8306 三菱UFJ、9434 ソフトバンク、130A Veritas In Silico、J-REIT 8 銘柄（8951, 8952, 8953, 3462, 3283, 3269, 8963, 3281）。

| 項目                                     | 結果                                                                                                                                                                         | 仕様への反映                                                                                              |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 日足（`chart`, `1d`）                    | 1 リクエストで 2015 年以降の約 2,900 本が 170〜430ms で取れる。英字入りコード（`130A.T`）も取れる                                                                            | 1 銘柄 1 リクエストで全期間を取る                                                                         |
| 日足の価格の調整                         | **`close` など OHLC は分割調整済み**（例: トヨタ 2015-01-05 の終値 1,501.4 は 2021 年の 5:1 分割で割った値）。`adjclose` は分割 + 配当で調整した値。**未調整の値は返らない** | FR-D2 を「分割調整済みの値 + 分割イベントを保存し、未調整は分割係数で戻す」に変更                         |
| 配当（`events: div`）                    | 日付と金額が取れる。**金額も分割調整済み**（例: ソフトバンク 2024-03 の 4.3 円は 10:1 分割前の 43 円）                                                                       | 分割をまたぐ利回り計算は、保存値のままで整合する                                                          |
| 分割（`events: split`）                  | 日付と比率（`5:1` など）が取れる                                                                                                                                             | FR-D3 のまま                                                                                              |
| **当日の足**                             | 大引け後しばらく、最後の日足の **`close` が `null`**（高値・安値・出来高は入っている）。同じ時刻の一括気配（`quote`）には終値がある                                          | FR-D8 を追加: `close` が無い足は保存せず、一括気配で当日の足を補う                                        |
| 一括気配（`quote`）                      | 10 銘柄を 1 リクエスト・約 560ms。終値・始値・高値・安値・出来高・前日終値・PER・PBR・時価総額・発行済株式数・BPS・EPS・実績配当・英語名が入る                               | 指標の取得は銘柄ごとの `quoteSummary` をやめ、一括気配に寄せる（FR-F5 を P1 に）                          |
| 52 週高値・安値（`quote`）               | **当日の値幅が入っていて使えない**                                                                                                                                           | ローカルの日足から計算する（元からの方針）                                                                |
| 実績配当（`trailingAnnualDividendRate`） | 多くは正しいが、**3269 アドバンス・レジデンスで 0**（履歴には配当がある）                                                                                                    | Yahoo の利回り系の値は使わず、配当履歴から計算する                                                        |
| 予想配当（`dividendRate`）               | 値はあるが算出元が一貫しない（3462 は予想 6,852 < 実績 7,329、8058 は直近配当の 2 倍とも合わない）。会社予想と照合する手段が無い                                             | **予想配当利回りは載せない**。J-Quants（P3）で取れるようにする                                            |
| PER・PBR・時価総額                       | 株式・J-REIT とも取れる。赤字企業（130A）は PER が無い                                                                                                                       | 欠損の扱い（FR-SC8）を P1 に                                                                              |
| J-REIT の NAV 倍率                       | **取れない**。J-REIT の `priceToBook` は簿価ベースの 1 口あたり純資産で割った値（含み益を含む NAV ではない）                                                                 | REIT の PBR は「PBR（簿価）」と表示。NAV 倍率は P3（取得元が見つかれば）                                  |

| 上場廃止                                 | yahoo-finance2 の README によると、Yahoo は上場廃止になった銘柄の過去データも消す                                                                                            | ローカルのデータが唯一の記録になる。「全データの削除」で廃止銘柄の履歴を消すかを選べるようにする（FR-S6） |

### 2. 月足の長期系列（`interval=1mo`）

- 7203 は 1999 年から（332 本）、8951 は 2005 年から、9434 は上場（2018 年）から取れる。
- 月足の日付は UTC（前月末の 15:00 = 当月 1 日 0:00 JST）。**日本時間に直してから月を決める必要がある**（直さないと 1 か月ずれる）。
- 日本時間に直したうえで、2023-01〜2026-10 の 46 か月を日足からの集計と比べると、**高値・安値・終値・出来高はすべて一致**。不一致は 1 月の始値だけ（各銘柄 3〜4 か所、差は 1% 未満）。
- 当月の足は途中の値なので使わない。

→ **月足の長期系列は採用する**（FR-D7）。保存期間の範囲内は日足からの集計、それより前を月次系列で補う。

### 3. SQLite のライブラリ

2,000 銘柄 × 5 年（245 万行）と 10 年（490 万行）の日足を入れて比べた（WAL、`synchronous=NORMAL`、主キー `(code, date)` の `WITHOUT ROWID` 表）。

|                                     | better-sqlite3 13.1 | node:sqlite（Node 25） |
| ----------------------------------- | ------------------- | ---------------------- |
| 投入 5 年 / 10 年                   | 8.9 秒 / 20.7 秒    | 6.4 秒 / 13.9 秒       |
| 1 銘柄の全足の読み出し 5 年 / 10 年 | 0.97ms / 1.78ms     | 1.38ms / 3.55ms        |
| 2,000 銘柄の集計（直近 20 日）      | 318ms / 567ms       | 289ms / 640ms          |
| DB の大きさ 5 年 / 10 年            | 144MB / 289MB       | 同じ                   |

- Electron 45.3.1 では、node:sqlite（SQLite 3.53.4）が main と utilityProcess の両方で動いた。
- **node:sqlite を採用する**。ネイティブモジュールの再ビルドや asar からの展開が要らず、Electron と CLI（素の Node）で同じものが動く。性能差は要件に対して小さい。リポジトリ層に閉じ込め、必要なら better-sqlite3 に替えられるようにする。
- 日足の表を直接集計するスクリーニングは 2,000 銘柄で 300〜600ms かかり、NFR-P3（500ms）に余裕が無い。**銘柄ごとの指標を 1 行にまとめた表（`metrics`）を取得のたびに更新し、スクリーニングはその表だけを読む**（FR-S10）。

## 銘柄情報の配当込みの騰落率・最大下落率（P3。FR-I7）

2,000 銘柄 × 約 10 年の日足（架空、490 万行）で測った。

| やり方                                          | 全銘柄          | 1 銘柄 |
| ----------------------------------------------- | --------------- | ------ |
| 今の指標の再計算（直近 800 本を読む）           | 1,140ms         | 0.57ms |
| 全銘柄の指標に足す（1,250 本を読んで計算）      | 2,037ms（+79%） | 1.02ms |
| 800 本 + 5 年前の終値と配当落ちの前日を点で読む | 1,204ms（+6%）  | 0.60ms |
| 表示中の銘柄だけ（日付と終値の 1,250 本）       | —               | 0.63ms |
| 計算だけ（1,250 本の 1 回の走査）               | 228ms           | 0.11ms |

- 時間は読み出しでかかり、計算は安い。最大下落率は全部の足を読むので、全銘柄の指標に入れると更新のたびに約 0.9 秒増える。
- **表示中の銘柄だけ、その場で計算する**（`info.extra`）。古い日から新しい日へ 1 回なめて、配当込みの倍率・最大下落・過去 12 か月の配当の移動合計（利回りの範囲）を同時に求める（O(本数 + 配当の回数)）。
- スクリーナーの条件に使うときは、配当込みの 1・3 年は今の 800 本で、5 年は点で読むやり方で、ほとんど重くせずに足せる。最大下落率は必要になってから考える。
- チャートの配当込みの調整（`series.ts` の `adjust`）も、配当ごとに前の足を全部なめていた（O(本数 × 配当の回数)）のを、権利落ちの足ごとに割合をまとめて後ろから掛ける形（O(本数 + 配当の回数)）に直した。

## 常駐と自動起動（2026-11-16。FR-BG1〜BG8）

設計は [design-background.md](design-background.md)。elecdex の同じ機能を考え方だけ参考にした（コードは写さない。NFR-A6）。

- **判断は純粋な関数（`src/shared/background.ts`）、実行は main（`src/main/background.ts`）**。main は settings.json を判断のたびに読む（renderer から設定を送る IPC を作らない）。
- **サインイン時の起動と「通知領域に入れておく」は settings.json に持たない**。正は Run キーの値とその引数。Electron の `launchItems` は `args` を常に空で返すが、
  `getLoginItemSettings({ args: ['--hidden'] }).openAtLogin` は引数まで比べるので、引数が `--hidden` かは読み分けられる（実機での確認が要る）。
- **トレイのアイコンは、しまっている間だけ出す**。見えている間に通知領域からする操作が無く、設定を変えたときに main へ知らせる経路も要らない。GUID は渡さない（署名していない exe ではパスに結び付く）。
- **二度目の起動の意味は `additionalData` で渡す**（`second-instance` の `argv` は並びが変わることがある）。終了の途中で `--quit` を受けても何もしない（`app.quit()` をもう一度呼ぶと、`before-quit` の流し込みと Core の停止を待たずに終わる）。
- **インストーラは `customCheckAppRunning` で先に `--quit` を送る**。`customInit` はウィザードを開いただけで走り、取り消しても戻らないので使わない。`--quit` を知らない古い版を起こさないよう、動いているときだけ送る。
- **Windows のシャットダウンでは `before-quit` が来ない**。しまうときと `query-session-end` で保存の流し込みを始め、`session-end` で位置を書いて Core に止めるよう頼む。
- **位置を記録しない窓は、background が隠した窓として覚える**。Windows では最小化した窓も `isVisible()` が偽になる（E2E で確かめた）ので、見えるかどうかでは分けられない。
- **トレイのメニューと案内の文言は `src/shared/background.ts` に置く**（main は renderer の `i18n.ts` を読まない。Core が起動できないときのダイアログと同じく main の文言で、純粋な関数として L1 で確かめる）。
- 設計は Opus のサブエージェントに 2 回、実装を 1 回レビューしてもらい、実装のレビューでは隠して起動した直後に戻すとフリー N が隠れたまま残ること・前に出すときに最小化しておいたフリー N まで戻すことなどを直した（どれも先に E2E で再現した）。
- 設計は Opus のサブエージェントに 2 回レビューしてもらい、隠して作った窓で `maximize()` が窓を出してしまうこと・戻す経路がばらばらだったこと・読み取り専用で画面とファイルがずれることなどを直した。
