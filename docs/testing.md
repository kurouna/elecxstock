# テストの作り（テストアーキテクチャ）

elecxstock のテストの層・置き場所・共通の部品・きまり。**実装を足す・直すときは、この文書に沿ってテストを足す・直す**（CLAUDE.md「テスト」）。
作り直しの計画と経緯は [test-plan.md](test-plan.md)、要求のテスト方針は [requirements.md](requirements.md) §11。

## 1. 層

いちばん安い層で確かめる。下の層で確かめられることを上に上げない。

| 層                      | 何を確かめるか                                                                                                                                 | 置き場所                                            | 実行                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------ |
| L1 純粋な関数           | 指標・足の集計・営業日・権利確定日・保有の計算・CSV・条件の評価・アラートの判定・分割の換算・条件の値の表示と入力・再計算のきっかけ            | `tests/unit/shared/`・`core/`・`renderer/`・`main/` | Vitest（project `unit`） |
| L2 登録表               | 指標・アクション・利用者のデータを書くメソッド・文言・再計算のきっかけが、すべての項目について整合すること。指標の性質の表のスナップショット   | `tests/unit/registry/`                              | Vitest（project `unit`） |
| L3 Core の結合          | `CoreService` をスタブと SQLite で動かす。取得・更新・分割・取り直し・保存期間・削除・移行・利用者のデータ・アラート・要求の処理（`dispatch`） | `tests/unit/core-int/`                              | Vitest（project `int`）  |
| L4 画面のロジックの結合 | `src/renderer/lib`・`stores` の関数を、製品と同じ経路で Core につないで動かす（一覧の列・保有の評価・Core との突き合わせ）                     | `tests/unit/renderer-int/`                          | Vitest（project `int`）  |
| L5 E2E                  | Electron をキーボードで操作する。フォーカス・ペインの操作・状態の変化への追従・重なり・永続化と再起動・複数の窓・時間の経過・見た目の回帰      | `tests/e2e/`                                        | Playwright `_electron`   |
| L6 契約                 | 実際の Yahoo・JPX（`LIVE=1`。値は保存しない）                                                                                                  | `tests/contract/`                                   | Vitest                   |

- L4 は Node で動くので `$effect` は動かない。L4 で確かめられるのは「状態を変えてから関数を呼ぶと正しい値が返る」まで。
  画面が状態の変化に追従するか（`$effect` の依存）は、きっかけを store の関数（`screenInputs()`）にまとめて L2 で確かめ、画面がそれを使っていることを L5 で確かめる。
- **コンポーネント（`.svelte`）に計算・変換・判定を書かない**。表示と入力の変換、欄やボタンを出すかの判定、再計算のきっかけは `src/shared/` か `src/renderer/lib/` の
  関数にし、L1・L2 で確かめる。同じ働きのコンポーネント（スクリーナーとアラートのダイアログ）は同じ関数を呼ぶ（例: `src/shared/conditionInput.ts`）。

## 3. 時刻

- 全テストの基準日時は **2026-11-13（金）18:00 JST**（`src/shared/clock.ts` の `TEST_NOW`）。テストの結果が今日の日付で変わらない。
- E2E とアプリは環境変数 `ELECXSTOCK_NOW=<ISO 8601>`（**スタブのプロバイダのときだけ効く**）。main がずれを 1 回だけ計算し、Core と renderer に渡す。
  `Date` は止めずにずらす（引数なしの `new Date()`・`Date.now()`・`Date()` だけ）。
- 単体は setupFiles が基準日時にする。時間を進めるテストは `vi.useFakeTimers({ toFake: ['Date'], now, shouldAdvanceTime: true })`（タイマーは止めない）か、
  関数に日付を渡す。E2E は `ELECXSTOCK_NOW` を変えて再起動する。

## 4. 観点

機能ごとに、すべての観点を検討する。当てはまらない観点は理由がわかるようにする。

| 記号 | 観点                 | 例                                                                          |
| ---- | -------------------- | --------------------------------------------------------------------------- |
| N    | 正常                 | 条件に合う銘柄が出る                                                        |
| B    | 境界                 | 60 本 / 61 本、3/31 / 4/1、今日 / 昨日                                      |
| X    | 異常・無効           | 壊れたファイル、無効な条件、読めない入力                                    |
| M    | 欠損・空             | 指標が無い、保有 0 件、結果 0 件                                            |
| U    | 単位・表示           | 円・万円・億円、% とポイント、日英                                          |
| S    | 状態の変化           | 保有・★・ウォッチリスト・スクリーン・設定を変えたあと、ほかの画面が追従する |
| I    | 初期状態・読み込み順 | 起動直後、遅れて届く指標の前と後、開いていないタブ                          |
| T    | 時間の経過           | 保存した日付を過ぎる、次の営業日                                            |
| P    | 永続化               | 保存 → 再起動、書き出し → 取り込み、元に戻す、移行                          |
| W    | 複数の窓             | フリー N で読むだけ、1 枚目への通知                                         |
| D    | 分割・配当           | 分割の前後、権利落ち、未調整・配当込み                                      |
| K    | キー操作             | キーだけで届く、IME の変換中は無視、フォーカスの戻り先                      |
| O    | 重なり               | 見えている操作の要素がふさがれていない                                      |
| F    | 速さ                 | NFR-P の上限                                                                |

## 5. 書き方のきまり

1. **データはすべて架空**（CLAUDE.md「テスト」）。実際の市場データを使わない・コミットしない。
2. **`describe` の名前に要求の ID を入れる**（例: `describe('取り直し（FR-S7, S11, FR-D3）', …)`）。`FR-H7〜H9`・`FR-AL3・AL4` の書き方も読む。
3. **登録表に足したら、登録表のテストが自動で対象にする**。指標の性質の表（`tests/unit/registry/__snapshots__/field-properties.txt`）が変わったら、
   `npx vitest run -u tests/unit/registry` で作り直し、差分を目で確かめてからコミットする。
4. **同じ値を 2 か所で出すなら、突き合わせる**（例: `tests/unit/core/differential.test.ts`・`tests/unit/renderer-int/columns.test.ts`）。境界の組で回す。
5. **例ではなく性質で書けるときは性質で書く**（表示 → 入力 → 表示が元に戻る、すべての指標で など）。期待値を同じ登録表から導かない。
6. **Core を呼ぶときは `core.call()`**（製品と同じ検証と構造化複製）。`svc.call()` は Core の中の値を共有するので、前の結果があとの変更で変わる。
7. **E2E はキーボードだけで操作する**（重なりのテストの `click({ trial: true })` だけが例外）。ダイアログの開閉・フォーカスの移動のあとは、移動先を `expect` してから次のキーを押す。
   固定の待ち（`waitForTimeout`）を足さない。キーを速く押して落ちるなら、まずアプリの不具合かを切り分ける。
8. **E2E の 1 件は 1 つの流れ**。準備の操作は userData を書いて省く。1 件 10 秒を超えたら分けるか、下の層に移す。
9. **時刻に頼るテストは基準日時から書く**。`new Date()` の今日を期待値に使わない。

## 6. 実装を足す・直すときの手順

1. 変える要求の ID を requirements.md で確かめる。
2. **不具合を直すときは、先に再現するテストを書いて落ちることを確かめ**、直して通す。
3. 変える箇所に当てはまる層（§1）と観点（§4）を選び、テストを足す・直す。
   - 計算・変換・判定 → L1（コンポーネントの中にあれば、先に `lib/`・`shared/` に出す）
   - 指標・アクション・メソッド・文言を足す → L2 が自動で対象にする（スナップショットの差分を確かめる）。利用者のデータを書くメソッドは `CHANGES`・`SCREEN_REBASE`
     （または `tests/unit/registry/changes.test.ts` の理由の表）に入れる
   - Core の取得・保存・ジョブ・要求 → L3
   - 画面のロジックと Core の値の関係 → L4
   - キー操作・フォーカス・描画・状態の変化への追従・再起動・複数の窓 → L5
4. **同じ作りの箇所を検索する**（スクリーナーとアラートのダイアログ、Screener・ChartGrid・Watchlist など）。同じ関数にまとめるか、同じテストを足す。
5. `npm run verify`（lint・型・単体・要求の ID）と、画面を変えたら `npm run build` のあと `npx playwright test` を通す。
6. 要求の ID のテストが増えたら `node scripts/trace.mjs --update`、カバレッジが上がったら `node scripts/coverage-check.mjs --update` で基準を上げる。

## 7. 漏れを見つける仕組み

| 仕組み                         | コマンド                                                       | 落とすとき                                                                                                                                    |
| ------------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 要求の ID とテストの突き合わせ | `npm run trace`（`verify` に入る。`--list` でテストの無い ID） | テストにある ID が requirements.md に無い。テストも除外（`tests/trace-exempt.json`）も無い ID が基準（`tests/trace-baseline.json`）より増えた |
| カバレッジ                     | `npm run coverage`（CI の unit ジョブ）                        | フォルダごとの行のカバレッジが基準（`tests/coverage-baseline.json`）から 1 ポイントより下がった                                               |
| 登録表の網羅                   | `npm test`                                                     | 指標・アクション・メソッドの分類が欠けた                                                                                                      |
| 指標の性質の表                 | `npm test`                                                     | スナップショットと違う（意図した変更なら作り直す）                                                                                            |

## 8. 速さ

| 対象                         | 予算                                                                                                                                                              | 方策                                                                                                                                                                                 |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 単体（`npm test`）           | 10 秒以内                                                                                                                                                         | 種の DB を 1 回だけ作り、結合のテストは写しを使う。純粋な関数だけなら `npm run test:fast`（3 秒前後）                                                                                |
| E2E（`npx playwright test`） | 手元で 60 秒以内（ビルドは別）・CI で 4 分以内。**2026-11-15 時点で手元 約 130 秒（105 件）**。並列の間は CPU が張り付き、約 2.5 コア分を Windows Defender が使う | 種の userData の写しから起動、固定の待ちなし、並列（project `parallel`）。OS のフォーカスに頼るもの（複数の窓・ドロワー）と見た目の回帰は直列（project `serial`。`parallel` のあと） |

E2E の一部だけを回すときは `npx playwright test <ファイル> --project=parallel`（直列のものは `--project=serial --no-deps`。指定しないと `dependencies` で並列の組も全部走る）。

遅いテストは Vitest（500ms 超）と Playwright（`reportSlowTests`）が出す。予算を超えたら、分けるか下の層に移す。
