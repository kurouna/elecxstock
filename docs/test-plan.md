# テスト計画

elecxstock の単体テスト・E2E を、レビューの回ごとに足してきた形から、要求（`FR-` / `NFR-`）と層に沿った形に作り直す。
この文書は、何をどの層で確かめるか・どう速く回すか・漏れをどう見つけるかを決める。[requirements.md](requirements.md) §11 の方針を具体化したもの。

## 1. 背景: レビューで見つかった不具合がテストで見つからなかった理由

| #   | 不具合                                       | 見つからなかった理由                                                                        |
| --- | -------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1   | スクリーナー・アラートの金額の単位           | 変換がコンポーネント（`.svelte`）の中にあり、どのテストも見ていない                         |
| 2   | 実行時に計算する指標の「欠損を含める」が無い | 同上                                                                                        |
| 3   | 結果表に実行時に計算する指標の列が無い       | 登録表のすべての指標について列があるかを確かめていない                                      |
| 4   | 条件を選ぶダイアログの ✓ が付かない          | E2E が「足したあと」の表示を見ていない                                                      |
| 5   | 5 年の増配率が銘柄情報とスクリーナーで違う   | 同じ値を 2 か所で計算しているのに突き合わせていない。既定の保存期間（5 年）のときだけずれた |
| 6   | 無配に転じた年の増減配率                     | 境界・異常の例が無い                                                                        |
| 7   | 権利付最終日を過ぎたあと、次の更新まで空く   | 時間が進んだ場合を確かめていない。E2E・Core の結合では時刻を変えられない                    |
| 8   | 結果 0 件の知らせがクリックをふさぐ          | E2E はキーボードだけなので、重なりで押せない不具合は見つからない                            |
| 9   | 保有タブを開く前の保有割合の分母             | 状態が温まった（必要な指標が届いた）あとでしか確かめていない                                |
| 10  | 保有を変えてもスクリーナーが走り直さない     | 再実行のきっかけが `.svelte` の `$effect` の依存にあり、どのテストも見ていない              |

あわせて、テストのファイルがレビューの回ごと（`review-v005`・`layout-fixes` など）で、どの要求をどこで確かめたか追えない。

## 2. 方針

1. **いちばん安い層で確かめる**。純粋な関数 → 登録表 → Core の結合 → 画面のロジック → E2E の順に、下で確かめられることを上に上げない。
   E2E は「プロセスをまたぐ」「キー操作とフォーカス」「描画・重なり」「状態の変化への追従」「永続化・再起動・複数の窓」に使う。
2. **コンポーネントに計算・変換・判定を書かない**。表示と入力の変換、ボタンや欄を出すかの判定、再計算のきっかけの集合は `lib/` か `shared/` の関数にし、
   同じ働きのコンポーネント（スクリーナーとアラートのダイアログなど）は同じ関数を呼ぶ。コンポーネントは関数を呼んで並べるだけにする。
3. **登録表で回す**。指標（`FIELDS`）・アクション（`ACTIONS`）・ペイン（`WIDGETS`）・利用者のデータを変えるメソッド（`CHANGES`・`SCREEN_REBASE`）・文言は、
   「すべての項目について」確かめる。項目を足せば自動で対象になる。ただし期待値を同じ登録表から導くと同語反復になるので、
   指標ごとの性質（単位・入力の倍率・1 株あたりか・欠損のトグル・相対の相手・アラートで使えるか・列の有無）は**1 枚の表のスナップショット**にし、
   足す・直すと差分が出て人が目で確かめる。往復（表示 → 入力 → 表示）のような性質のテストは別に持つ。
4. **2 つの経路は突き合わせる**（差分テスト。§5）。例 1 つではなく、境界のフィクスチャの組で回す。
5. **冷えた状態から確かめる**。画面のロジックの突き合わせは、起動直後に読む分だけの状態から始め、遅れて届くもの（`ensureMetrics` など）の前と後の両方で確かめる。
6. **時刻を固定する**（§3.2）。全テストの基準日時を 1 つ決め、時間の経過はそこから進める。
7. **観点の表（§4・§8）を漏れを見つける主役にする**。機能ごとにすべての観点を検討し、当てはまらない観点は「対象外」と理由を書く。
8. **要求に紐づける**。`describe` の名前に要求の ID を入れる。ID の網羅は補助の指標として数える（§7）。
9. **速さを要求として扱う**（§6）。
10. **データはすべて架空**（CLAUDE.md の「テスト」）。

## 3. 層と置き場所

| 層                | 何を確かめるか                                                                                                                                                                                  | 実行                                 | 置き場所                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| L1 純粋な関数     | 指標・足の集計・営業日・権利確定日・保有の計算・CSV の読み取り・条件の評価・アラートの判定・分割の換算・表示と入力の変換・再計算のきっかけの集合                                                | Vitest（node）                       | `tests/unit/shared/`・`tests/unit/core/`・`tests/unit/renderer/` |
| L2 登録表         | 表どうし・表と画面の整合、指標の性質の表のスナップショット                                                                                                                                      | Vitest（node）                       | `tests/unit/registry/`                                           |
| L3 Core の結合    | `CoreService` をスタブのプロバイダと一時フォルダの SQLite で動かす。取得・更新・分割・取り直し・保存期間・削除・利用者のデータ（移行・壊れたファイル・書き出しと取り込み）・アラート・DB の移行 | Vitest（node）。種の DB の写しを使う | `tests/unit/core-int/`                                           |
| L4 画面のロジック | `lib/`・`stores/` の関数を、製品と同じ窓口（§3.3）で Core につないで動かす。列・並べ替え・保有の評価・突き合わせ                                                                                | Vitest（node）                       | `tests/unit/renderer-int/`                                       |
| L5 E2E            | Electron をキーボードで操作する。フォーカス・ペインの操作・状態の変化への追従（§8.1）・重なり（§8.2）・永続化と再起動・複数の窓・時間の経過・見た目の回帰                                       | Playwright `_electron`               | `tests/e2e/`                                                     |
| L6 契約           | 実際の Yahoo・JPX（`LIVE=1`。値は保存しない）                                                                                                                                                   | Vitest                               | `tests/contract/`（変えない）                                    |

L4 は node で動くので、`.svelte.ts` はサーバ向けにコンパイルされ `$effect` は動かない。L4 で確かめられるのは「状態を変えてから関数を呼ぶと正しい値が返る」まで。
状態の変化に画面が追従するか（`$effect` の依存）は、再計算のきっかけを store の関数にまとめて L1 で確かめ、画面がそれを使っていることを L5 の表（§8.1）で確かめる。

### 3.1 共通の部品

- `tests/support/fixtures.ts`: 日足・配当・分割・銘柄・指標の行・保有を作る関数。評価日を引数で受ける。境界の組（上場 5 年未満・無配に転じた・期間内の分割・保存期間 5 年と 10 年・保有 0 件）を名前付きで持つ。
- スタブ（`stub.ts`）にも境界の架空の銘柄を足す: 無配に転じた銘柄・上場 1 年未満の銘柄（L3〜L5 でも通るように）。日足の欠けは取りこぼしの確認（L3）で扱う。
- `tests/support/core.ts`: `seededCore()`（種の DB の写しで `CoreService` を作る）・`idle(svc)`。
- `tests/support/bridge.ts`: §3.3 の窓口。
- `tests/support/seed.ts`（Vitest の globalSetup）: 基準日時に時刻をずらしてから（§3.2 の関数）スタブで初回取得を済ませ、`svc.close()` のあとに DB を一時フォルダに置く。実行をまたいでは残さない（毎回作る）。
- `tests/support/setup.ts`（Vitest の setupFiles）: すべてのファイルを既定で基準日時にする（§3.2 の関数。書き忘れたファイルが実時刻で動かないように）。
- `tests/e2e/support/`: `launch()`（種の userData の写しから起動）・`keys()`・`ready()`・よく使う操作。
  globalSetup で、基準日時のアプリを 1 回起動して初回取得を済ませ、終了してから DB と利用者の JSON だけを種にする（Chromium のプロファイルは写さない）。
  `out/` が `src/` より古ければ、globalSetup で止める（古いビルドで合格しない）。
  並列で窓が重なっても描画が止まらないように、`launch()` は Chromium の引数 `--disable-renderer-backgrounding`・`--disable-backgrounding-occluded-windows`・`--disable-features=CalculateNativeWinOcclusion` を付ける
  （アプリは `backgroundThrottling: false`）。土台を作る段階で、worker 6・窓が重なった状態で 1 回試す。

### 3.2 時刻

- 環境変数 `ELECXSTOCK_NOW=<ISO 8601>` を足す。**スタブのプロバイダのときだけ効く**。`Date` を基準日時からのずれで進める（止めない）。
  ずれは main が 1 回だけ計算し、Core（環境変数）と renderer（preload への引数）に同じずれを渡す（プロセスごとに計算すると起動の時差でずれる）。
  `Date` をずらす関数（`src/shared/clock.ts`）は、製品の入口・Vitest の globalSetup と setupFiles が共有する。
- スタブはずらした `Date` を読む。系列のキャッシュのキーは銘柄コードと末日にする（時刻を進めると、その日までの系列になる）。
- 基準日時は **2026-11-13（金）18:00 JST**（大引けのあと・平日。`TEST_NOW`）。時間の経過のテストはそこから進める。E2E は `ELECXSTOCK_NOW` を変えて再起動、
  単体は `vi.useFakeTimers({ toFake: ['Date'] })` か関数の引数（`setTimeout` は止めない。止めるとジョブが進まない）。
- ずらすのは引数なしの `new Date()`・`Date.now()`・`Date()` だけ（`Proxy` で包む）。ずらす処理は入口の最初の `import`（`clock-init.ts`）で行う。

### 3.3 L4 の窓口（製品と同じ経路）

- `worker.ts` の「検証（zod）→ 呼び出し → 結果」を `dispatch(svc, msg)` に出し、worker と L4 の窓口の両方が使う。
- 窓口は引数と結果を `structuredClone` する（Svelte の Proxy をそのまま送ると製品では落ちる）。Core のイベント（`data.updated`・`user.changed`）を `on` に流す。
- main の機能（`saveText`・`openFile` など）は記録するだけの偽物にする。

## 6. 速さ

### 6.1 現状（2026-11-15 計測）

- 単体: 27 ファイル・186 件、5.5 秒（うち 4 ファイルがそれぞれ初回取得に約 3 秒）。
- E2E: 53 件、3.4 分。直列。テストのたびに初回の確認と初回取得（約 1.9 秒）を待ち、`keys()` は 1 キーごとに 60ms 待つ。
  種の userData の写し（約 50ms）から起動すると、操作できるまで約 0.4 秒。

### 6.2 方策

| 方策                                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E2E: 種の userData の写しから起動する。初回の確認・初回取得を確かめるテストだけ空の userData                                                                                                                                                                                            |
| E2E: `keys()` は 1 キーごとに、描画 1 回分（`requestAnimationFrame`）と 20ms の早いほうだけ待つ。ダイアログの開閉・フォーカスの移動のあとは、移動先を `expect` してから次の `keys` を呼ぶ。待ちを外して落ちたら、テストに待ちを足す前にアプリの不具合（速く打つと落ちる）かを切り分ける |
| E2E: `fullyParallel`。手元の worker は CPU の半分（上限 6）、CI（Windows のランナーは 4 コア）は 2。OS のフォーカスに頼るテスト（複数の窓・窓の切り替え・ドロワー）と見た目の回帰は、`dependencies` で並列のあとに回す直列の project                                                    |
| E2E: 1 件 = 1 つの流れ。長い流れは分ける。準備の操作は userData のレイアウトを書いて省く                                                                                                                                                                                                |
| E2E: `trace: 'on-first-retry'`、CI だけ `retries: 1`。テスト中の `page.screenshot` は消す。`timeout` 30 秒・`expect` 5 秒                                                                                                                                                               |
| 単体: 種の DB を globalSetup で 1 回作り、L3・L4 は写しを使う                                                                                                                                                                                                                           |
| 単体: 純粋な関数だけを回す `npm run test:fast`（Vitest の project）                                                                                                                                                                                                                     |
| CI: 単体・E2E を別のジョブにして並べる                                                                                                                                                                                                                                                  |
| 遅いテストは Vitest の `slowTestThreshold`・Playwright の `reportSlowTests` で出す                                                                                                                                                                                                      |

### 6.3 予算

- 単体: すべてで 10 秒以内。
- E2E: 手元で 60 秒以内（`npm run build` は別）、CI で 4 分以内。1 件 10 秒を超えるテストは分けるか下の層に移す。

## 7. 漏れを見つける仕組み

1. **観点の表（§8）**: 機能ごとに §4 の観点をすべて検討した結果。主役。
2. **要求の ID**: `scripts/trace.mjs` が requirements.md の ID とテストの `describe` に書いた ID を突き合わせ、一覧を出す。`npm run verify` で落とすのは次のときだけ。
   - テストにあるが requirements.md に無い ID（古い・打ち間違い）。
   - 確かめも除外もされていない ID の数が、`tests/trace-baseline.json` より増えたとき（減ったら基準を更新する）。
   - テストで確かめない要求（配布・手作業・文書だけ）は `tests/trace-exempt.json` に理由とともに書く。
3. **カバレッジ**: `@vitest/coverage-v8`（`npm run coverage`。CI のジョブだけで回し、`verify` には入れない）。下限は「今の値から下げない」。
   下限はフォルダごと（`src/core`・`src/shared`・`src/renderer/lib`）に持ち、1 ポイントの幅を持たせる（ファイル間でコードを移すだけで落ちないように）。
   `providers/yahoo.ts`・`providers/jpx.ts`・`worker.ts`（契約テストと E2E でしか通らない）は除く。
4. **不具合を直すときのきまり**: 先に再現するテストを書いて落ちることを確かめ、直して通す。同じ作りの箇所を検索し、同じ関数にまとめるか同じテストを足す。

## 9. 移し替えの手順

1. 計画の土台（§3.1〜§3.3）を作る: `ELECXSTOCK_NOW`・スタブの `now`・`dispatch`・種・`launch` / `keys`・Playwright と Vitest の設定。
2. コンポーネントの計算をまとめる（§2 の 2）: 条件の値の表示と入力（`conditionValueText` / `parseConditionValue`）、欠損のトグルを出すか、
   再計算のきっかけ（`screenInputsKey()`）を `lib/` に出し、Screener・AlertForm・ChartGrid・Watchlist がそれを呼ぶ。
3. 機能ごとに新しいファイルを作り、古いファイルを残したまま移す。移し終えたファイルから古いものを消す。確かめていた事柄は落とさない
   （古いファイルの `it` の一覧と、移し先を突き合わせる）。
4. 新しいテスト（§5・§8 の「新」）を足す。
5. requirements.md の §11・NFR-CI5・NFR-Q10 を、この計画（性能・見た目の回帰の範囲）に合わせて直す。
